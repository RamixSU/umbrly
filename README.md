# Umbrly 0.2 "Waffles"

**Umbrly** — интерпретируемый и компилируемый язык программирования для Windows. Написан на C++17
с модульной архитектурой (лексер → парсер → AST → дерево-интерпретатор либо транспилятор в C++)
и содержит встроенный слой функций-обёрток над WinAPI (консоль, окна, файлы, буфер обмена, звук,
процессы, мышь/клавиатура), классы (`CLASS`/`SELF`), модули (`LOAD`), 102 встроенные функции.

## Модули — `LOAD`

```
LOAD ИМЯ_БИБЛИОТЕКИ_ИЛИ_МОДУЛЯ
```

`LOAD` ищет файл `ИМЯ.umb` сначала рядом со скриптом, который его подключает (локальные модули
проекта), а если там нет — в папке `lib/` рядом с `umbrly.exe` (общая для всех проектов
"стандартная библиотека"; в комплекте уже есть `lib/MathX.umb`). Все `FUNC`/`CLASS` из найденного
файла становятся доступны глобально, без пространств имён — как обычный код, вставленный на место
`LOAD`. Повторный (в том числе циклический через цепочку других `LOAD`) импорт одного и того же
модуля тихо схлопывается в пустоту, вместо повторной регистрации функций.

`LOAD` допустим только на верхнем уровне файла (не внутри `IF`/`WHILE`/`FUNC`) и разрешается ещё
на этапе загрузки файла — до выполнения и до компиляции, поэтому работает одинаково что в `-r`,
что в `-b`/`-c`. Пример — `examples/imports_demo.umb` (использует и `lib/MathX.umb`, и локальный
`examples/geometry_lib.umb`).

## CLI

```bat
umbrly                                интерактивный REPL
umbrly file.umb                       запуск через интерпретатор (как -r)
umbrly -r file.umb   | run file.umb            запуск через интерпретатор
umbrly -b file.umb [out.exe] | build file.umb [out.exe] | compile file.umb [out.exe]
                                       компиляция в нативный .exe (нужен g++/MinGW-w64)
umbrly -c file.umb [out.cpp]          транспиляция в C++ без вызова g++ (отладочный вывод)
umbrly -t file.umb                    проверка синтаксиса (лексер+парсер), без выполнения
umbrly -ir file.umb                   вывод AST в текстовом виде
umbrly -d file.umb | -trace file.umb  запуск с построчной трассировкой выполнения
umbrly -v | --version                 версия
umbrly -h | --help                    справка
umbrly --info                         информация о языке и бэкенде
```

`-p`/`pack` (упаковка проекта в портативный дистрибутив) пока не реализованы — сознательно
отложено как отдельная задача: неочевидно, что вообще должно входить в "пакет" для однофайлового
скриптового языка без концепции ассетов, эта развилка заслуживает отдельного обсуждения, а не
поспешной реализации в довесок к остальному.

## Компиляция в машинный код

`-b`/`-c` транспилируют AST программы в C++, который либо просто сохраняется (`-c`), либо сразу
собирается вызовом `g++` в нативный `.exe` (`-b`) — `umbrly.exe` сам находит компилятор (сначала
`g++` в PATH, затем типичный путь установки MSYS2) и вызывает его через `CreateProcessW`, как это
делает `build.bat`.

**Что действительно становится нативным кодом:** управляющие конструкции — `IF`/`WHILE`/`FOR`
(включая `BREAK`/`CONTINUE`, которые превращаются в настоящие `break`/`continue`), `FUNC`
(в реальные C++-функции с прямыми вызовами друг друга, без обхода AST), `TRY`/`CATCH` (в
`try`/`catch` вокруг того же `UmbrlyError`), локальные переменные (в обычные C++-переменные
`Value` вместо поиска по хеш-таблице). Именно отсюда честный выигрыш в скорости: `FIB(27)`
рекурсивно — 390–540 мс в интерпретаторе против ~30 мс в скомпилированном виде на одной и той же
машине (см. [examples/benchmark.umb](examples/benchmark.umb)).

**Что осталось прежним runtime-объектом `Interpreter`, вызываемым из сгенерированного кода:**
арифметика/сравнения (`interp.opAdd`, `interp.opLt`, ...), приведение типов, встроенные функции
(`interp.callFunction`) и **методы классов** — тело метода как выполнялось обходом AST, так и
выполняется, даже в скомпилированной программе (сгенерированный `.exe` встраивает исходный текст
`.umb` как строку и на старте заново парсит его именно ради `CLASS` — `Interpreter::registerAllDefs`).
Это осознанный компромисс: полная нативная компиляция классов (с диспетчеризацией методов без
интерпретации) — отдельная, гораздо более объёмная задача, не оправданная для первой версии
компилятора.

`-t` — только лексер+парсер, без выполнения (быстрая проверка синтаксиса, например в CI).
`-ir` — печатает AST в текстовом виде (для отладки самого языка, не пользовательских программ).
`-d`/`-trace` — идентичны на сегодняшний день: печатают номер строки перед каждым выполняемым
оператором интерпретатора.

## Архитектура

Классический конвейер интерпретатора, каждый этап — отдельный модуль:

```
include/            заголовки (объявления)             src/                 реализация
  errors.h            UmbrlyError, fail(), failAt()       lexer.cpp            tokenize(): текст -> токены
  value.h             Value: INT/FLOAT/STR/BOOL/ARR/NIL   parser.cpp           токены -> AST (Block), сегменты строк
  lexer.h             Token, TokType, tokenize()          ast.cpp              eval()/exec() для каждого узла AST
  ast.h               узлы AST (Expr/Stmt), Signal —      interpreter.cpp      переменные, функции, вызовы
                      только объявления, без логики       builtins.cpp         математика/строки/массивы/типы
  parser.h            parseProgram()                      winapi_bindings.cpp  MessageBox, файлы, консоль, мышь...
  interpreter.h       класс Interpreter                   main.cpp             CLI: запуск файла или REPL
  builtins.h          registerCoreBuiltins()
  winapi_bindings.h   registerWinApiBuiltins()
```

Поток данных: `main.cpp` читает исходный текст → `tokenize()` строит поток токенов →
`parseProgram()` строит дерево (`Block` = `vector<StmtPtr>`) → `Interpreter::run()` регистрирует
все `FUNC` (чтобы работали вызовы "вперёд") и выполняет операторы, вызывая `Stmt::exec()` /
`Expr::eval()`, реализованные в `ast.cpp`. Встроенные функции (обычные и WinAPI) — это просто
записи в таблице `Interpreter::builtins_` с сигнатурой `Value(Interpreter&, vector<Value>&, int line)`,
поэтому оба модуля (`builtins.cpp`, `winapi_bindings.cpp`) не знают друг о друге и не знают
о парсере — только об `Interpreter`.

### Производительность

Два узких места, характерных для наивных tree-walking интерпретаторов, устранены целенаправленно:

1. **`BREAK`/`CONTINUE`/`RETURN` не бросают C++-исключений.** `Stmt::exec()` возвращает
   `enum class Signal { None, Break, Continue, Return }` — обычное возвращаемое значение,
   которое "всплывает" через `execBlock()` до ближайшего цикла или до `callFunction()`.
   Раскрутка стека исключений в C++ не бесплатна, а `CONTINUE` в цикле — это не исключительная
   ситуация, а часть нормального потока управления. Значение `RETURN` временно хранится в
   `Interpreter::pendingReturn_` и забирается вызывающим кодом функции (`takePendingReturn()`).
   Настоящие ошибки (`UmbrlyError`, например деление на ноль) по-прежнему обычные исключения —
   они действительно исключительны и не встречаются на каждой итерации.
2. **Подстановки `[выражение]` разбираются один раз, при парсинге программы**, а не при каждом
   вычислении строки. `Parser::buildStringSegments()` превращает строковый литерал в список
   готовых фрагментов (`StringSegment`: либо литеральный текст, либо уже разобранный `ExprPtr`);
   `StringLitExpr::eval()` только вычисляет уже готовые выражения и склеивает результат. Раньше
   `PRINT: "[INT_I]"` внутри цикла заново токенизировал и парсил `INT_I` на каждой итерации.

Плюс мелкие точечные оптимизации: `Value::toString()` для `FLOAT` использует `snprintf` вместо
`std::ostringstream` (без аллокации потокового буфера и обращений к locale), сборка идёт с
`-O3 -flto` (кросс-файловый инлайнинг между всеми `.cpp`). [examples/benchmark.umb](examples/benchmark.umb)
прогоняет 300 000 итераций `FOR` с `CONTINUE` и интерполяцией, рекурсивный `FIB(27)`
(~1.3 млн вызовов) и 200 000 переразборов строки с подстановкой — на типичной машине укладывается
в районе секунды суммарно.

Что сознательно **не** сделано: возврат переменных по ссылке из `getVar()` — это дало бы копейки
на числах, но с текущим `vector<unordered_map<...>>` для стека областей видимости несёт риск
инвалидации ссылок при `push_back` нового кадра вызова (вектор может переехать в памяти).
Правильно это делать через `vector<unique_ptr<Scope>>`, но это отдельная переработка, которая
не оправдана без профилирования конкретной программы, где это стало бы узким местом.

### Почему всё на C++, а не C++ + ассемблер

Узкое место интерпретатора — обход AST и системные вызовы (WinAPI, консоль, файлы), а не арифметика.
`g++ -O2` уже генерирует код, который ручная ассемблерная вставка не ускорит заметно, а сборка
отдельных `.asm`-модулей под MinGW/x64 добавляет сложности с calling conventions без ощутимой
выгоды. Комбинирование C++/ASM имеет смысл для действительно горячих числовых циклов (кодеки,
рендеринг) — не для дерева разбора команд уровня `PRINT:`/`IF:`.

## Сборка и запуск

```bat
build.bat                          — собрать umbrly.exe (нужен g++ / MinGW-w64)
umbrly.exe examples\hello.umb      — выполнить программу
umbrly.exe                         — интерактивный режим (REPL), выход: EXIT
```

`build.bat` компилирует все файлы `src\*.cpp` с `-Iinclude` и линкует WinAPI-библиотеки
(`user32`, `shell32`, `winmm`, `advapi32`). Файлы программ — расширение `.umb`, кодировка UTF-8.

## Синтаксис языка

### Переменные — тип определяется префиксом имени

| Префикс  | Тип                       | Пример                     |
|----------|---------------------------|----------------------------|
| `INT_`   | целое число                | `INT_CYFRA = 67`          |
| `FLOAT_` | дробное число               | `FLOAT_PI = 3.14`         |
| `STR_`   | строка                     | `STR_IMYA = "Вова"`       |
| `BOOL_`  | логическое (`TRUE`/`FALSE`) | `BOOL_OK = TRUE`          |
| `ARR_`   | массив                     | `ARR_XS = [1, 2, 3]`      |
| `OBJ_`   | экземпляр класса           | `OBJ_P = Player("Вова")`  |

Присваивание всегда приводит значение к типу переменной (`BOOL_` — по истинности,
`INT_`/`FLOAT_` — численно, `STR_` — через `TOSTR`); несовместимые приведения (например,
строка в `INT_`) — ошибка времени выполнения с номером строки.

### Вывод и ввод

```umbrly
PRINT: "Hello World"
PRINT:                                       # пустая строка

INPUT: "Нажмите Enter..."                    # пауза, ждёт нажатия
INT_X = INPUT: "Введите число: "             # ввод с приведением к типу переменной
```

### Подстановка в строки — `[выражение]`

```umbrly
INT_CYFRA = 67
PRINT: "[INT_CYFRA] + [INT_CYFRA] = [INT_CYFRA + INT_CYFRA]"   # 67 + 67 = 134
```

Внутри `[...]` — полноценное выражение (вызовы функций, индексация массивов, всё что угодно).
Экранирование: `\n \t \r \" \\ \[ \]`. Для нужной кавычки внутри `[...]` (например, строкового
литерала в аргументе функции) её нужно экранировать как `\"` — интерпретатор сам разэкранирует
её перед повторным разбором вложенного выражения.

Если строка должна содержать буквальные квадратные скобки как текст (не подстановку —
например, тег вида `[OK]`), их обязательно нужно экранировать: `"\[OK\]"`. Без экранирования
`[OK]` будет воспринято как выражение — переменная `OK` — и приведёт к ошибке разбора.

### Выражения

Приоритет (по возрастанию): `OR` → `AND` → `NOT` → `== != < > <= >=` → `+ -` → `* / %` → `()`.
`+` со строками — конкатенация. `/` двух целых даёт целое, если делится нацело, иначе дробное.
`TRUE`/`FALSE`/`NIL` — литералы. Символьные альтернативы `&& || !` тоже работают.

### Условия и циклы

```umbrly
IF: INT_X > 10
    PRINT: "большое"
ELSE:
    PRINT: "маленькое"
END

WHILE: INT_X > 0
    INT_X = INT_X - 1
END

FOR: INT_I = 1 TO 10           # включительно; необязательный STEP (по умолчанию 1)
    PRINT: "[INT_I]"
END
FOR: INT_J = 10 TO 1 STEP -1
    PRINT: "[INT_J]"
END
```

`BREAK` и `CONTINUE` работают внутри `WHILE`/`FOR`. Использование их вне цикла —
ошибка разбора (`BREAK встречается вне цикла (WHILE/FOR)`), а не крах во время выполнения.

### Массивы

```umbrly
ARR_XS = [10, 20, 30]
PRINT: "[ARR_XS[0]]"           # 10
ARR_XS[0] = 99                 # присваивание по индексу
PUSH(ARR_XS, 40)
STR_LAST = POP(ARR_XS)
PRINT: "[LEN(ARR_XS)]"
```

**Присваивание копирует, вызов функции передаёт по ссылке.** `ARR_B = ARR_A` создаёт
независимую копию — изменения `ARR_B` не затронут `ARR_A`. А вот при передаче массива
параметром пользовательской `FUNC` или встроенной функции вроде `PUSH`/`SORT` ссылка на
тот же массив, поэтому `PUSH(ARR_X, v)` мутирует именно переданный `ARR_X`, без `RETURN`
и переприсваивания — как в Python или JavaScript. Если внутри своей функции нужно не
задеть массив вызывающего кода — явно склонируйте через `COPY(arr)`.

### Функции

```umbrly
FUNC FACT(INT_N):
    IF: INT_N <= 1
        RETURN 1
    END
    RETURN INT_N * FACT(INT_N - 1)
END

PRINT: "[FACT(5)]"             # 120
```

Параметры типизируются так же, как переменные (префикс имени). `FUNC` можно вызывать
до места объявления в файле — все функции регистрируются перед выполнением. Рекурсия
ограничена глубиной 256 вызовов (защита от зависания на бесконечной рекурсии).

### Классы

```umbrly
CLASS Player:
    STR_NAME = ""
    INT_HP = 100

    FUNC INIT(STR_N):          # конструктор — вызывается автоматически при создании
        SELF.STR_NAME = STR_N
    END

    FUNC TAKE_DAMAGE(INT_AMOUNT):
        SELF.INT_HP = SELF.INT_HP - INT_AMOUNT
    END

    FUNC IS_ALIVE():
        RETURN SELF.INT_HP > 0
    END
END

OBJ_P = Player("Вова")          # создание — обычный вызов, как в Python
OBJ_P.TAKE_DAMAGE(30)
PRINT: "[OBJ_P.STR_NAME]: HP=[OBJ_P.INT_HP], жив=[OBJ_P.IS_ALIVE()]"
```

- Поля — обычные типизированные переменные (`INT_`/`STR_`/`ARR_`/`OBJ_`/...) с
  выражением-значением по умолчанию, вычисляемым при каждом создании объекта.
- Методы — обычные `FUNC` внутри тела `CLASS`, с неявным первым именем `SELF`,
  указывающим на текущий экземпляр. Внутри метода `SELF.ПОЛЕ = значение` мутирует сам
  объект (в отличие от обычных функций, где присваивание скаляра меняет только
  локальную копию, — здесь это специально работает иначе, потому что через точку
  идёт явная мутация полей объекта, а не присваивание переменной).
- **Создание объекта — вызов `ИмяКласса(аргументы)`**, без отдельного ключевого слова
  `NEW`: если имя не совпало ни с одной пользовательской `FUNC`, интерпретатор проверяет,
  не зарегистрирован ли класс с таким именем, и создаёт экземпляр. Метод `INIT` (если
  объявлен) получает переданные аргументы и работает как конструктор; без `INIT` класс
  можно создавать только без аргументов.
- **Присваивание объекта — по ссылке**: `OBJ_B = OBJ_A` — это два имени одного и того же
  экземпляра (в отличие от массивов, которые при присваивании копируются). Изменение
  через любое из имён видно через оба.
- Поля и методы — публичные, наследования и модификаторов доступа нет. `CLASS` можно
  использовать до места объявления в файле (регистрируется заранее, как `FUNC`).

### Обработка ошибок — TRY / CATCH

```umbrly
TRY:
    INT_X = TOINT("не число")
CATCH: STR_ERR
    PRINT: "Поймали: [STR_ERR]"
END
```

*(нужна интерактивная рабочая область Windows; в headless-сессиях без десктопа может вернуть пустую строку)*

### WinAPI — файлы и папки
`FILE_READ(path)` `FILE_WRITE(path,text)` `FILE_APPEND(path,text)` `FILE_EXISTS(path)`
`FILE_DELETE(path)` `DIR_EXISTS(path)` `DIR_CREATE(path)`

### WinAPI — система, окружение, процессы
`ENV_GET(name)` `ENV_SET(name,value)` `COMPUTER_NAME()` `USER_NAME()` `SCREEN_WIDTH()`
`SCREEN_HEIGHT()` `TICK_COUNT()` `TIME_NOW()` `FIND_WINDOW(title)` `ACTIVATE_WINDOW(handle)`
`SHELL_OPEN(path)` `RUN(cmd) -> INT (код возврата)` `EXIT(code)`

### WinAPI — производительность
`CLOCK()` — монотонный счётчик высокого разрешения в секундах (`QueryPerformanceCounter`),
для замера времени работы своих скриптов. `CPU_COUNT()` — число логических процессоров.

## Сообщения об ошибках

Интерпретатор всегда сообщает номер строки и причину:

```
Ошибка (строка 5): неизвестная переменная 'INT_Y' (переменной ещё не присвоено значение)
```

`TRY`/`CATCH` перехватывает такие ошибки внутри программы, не прерывая её выполнение.
